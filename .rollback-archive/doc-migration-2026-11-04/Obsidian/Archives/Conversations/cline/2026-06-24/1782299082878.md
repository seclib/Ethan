# ETHAN Debug Mode — Architecture Design

## Aperçu architectural

Le mode debug est conçu comme une **couche d'observation instrumentée** qui s'interpose entre tous les composants du système sans modifier leur logique métier. Il repose sur le principe **d'instrumentation passive** : les composants existants ne sont pas modifiés, mais leurs flux sont interceptés, enrichis et rendus visibles.

```

│                                                                     │

│  │ - breakpoints     │  │ - memory inspect   │  │ - export      │   │

│                                  ▼                                   │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │                    Debug Bus (in-process)                     │   │
│  │  Proxies NATS, intercepts publish/subscribe en temps réel    │   │
```

## 1. Noyau du système debug

### 1.1 DebugBus — intercepteur d'événements

Le DebugBus s'interpose entre les composants et le NATS bus. Il enregistre tous les événements qui transitent, avec leur payload complet, sans modifier le flux.

```
Composant A ──► DebugBus ──► NATS
                    │
                    ▼
              TraceStore (mémoire + disque)
```

**Propriétés :**
- Proxy passif : les événements traversent normalement
- Capture : id, type, source, timestamp, payload, metadata
- Pas de modification : les événements ne sont jamais altérés
- Tags : le DebugBus ajoute `debug: true` aux metadata pour le traçage

### 1.2 TraceStore — stockage des traces

Stockage en anneau (ring buffer) pour éviter la consommation mémoire illimitée.

```
┌─────────────────────────────────────────┐
│            TraceStore                    │
│                                         │
│  Ring buffer (10 000 entrées max)       │
│  │  │  │  │  │  │  │  │  │  │  │  │   │
│  ▼  ▼  ▼  ▼  ▼  ▼  ▼  ▼  ▼  ▼  ▼  ▼   │
│  [ev1][ev2][ev3]...[evN]               │
│                                         │
│  Filtres :                               │
│  - par type d'événement                  │
│  - par source                            │
│  - par intervalle de temps               │
│  - par mot-clé dans le payload           │
│                                         │
│  Export : JSON, JSONL, texte             │
└─────────────────────────────────────────┘
```

**Capacités :**
- 10 000 événements en mémoire (configurable via `--debug-buffer`)
- Snapshot sur disque dans `~/.ethan/debug/`
- Recherche plein texte sur les payloads
- Filtrage par composant, type, intervalle

```python
def dispatch(argv, _debug=False, timeout=_COMMAND_TIMEOUT):
    # Si le mode debug est activé
    if _debug or os.environ.get("ETHAN_DEBUG"):

            result = fn(args)

            debug_session.report(error=e)
            raise
```

## 10. Principes de conception

1. **Non-intrusif** — Le mode debug est activé explicitement. Aucune instrumentation en production sans le flag `--debug` ou `ETHAN_DEBUG=1`.

2. **Zéro impact performance** — Les hooks debug sont des no-ops quand le mode est désactivé (vérification par booléen avant toute capture).

3. **Respect du BRAND_FEEL** — Tous les affichages suivent les règles : max 2 couleurs par ligne, max 3 icônes par section, pas de bruit décoratif.

4. **Respect de l'architecture existante** — Aucun composant existant n'est modifié dans sa logique. Les hooks s'interposent par proxy/wrapper.

5. **Buffer limité** — Ring buffer de 10 000 événements max. Pas de fuite mémoire possible.

6. **Exportable** — Toutes les traces peuvent être exportées pour analyse différée ou partage.

7. **Intégrable au pipeline CI** — `ethan debug --quiet --export` produit un fichier JSON analysable par des scripts.HAS_CHANGES
